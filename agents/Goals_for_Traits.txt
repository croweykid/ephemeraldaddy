Let me explain how I want it to work & where Traits is hopefully headed in its long term goal, then you can pitch me the most useful immediate migrations/refactoring and start undertaking it at once.

1) Traits needs to be accurate. I want it to really look at DB averages/norms and come back with relative values of any given particular chart relative to database norms. That's it's core function, however:

2)

a) Database norms can absolutely be established based off of a database of 2000+ people, which I have. What we're looking at right now is very much a developer version of the app, not a consumer-facing version of the app. It's increasingly clear to me that I can safely take a snapshot of my HUGE database ONCE to examine what norms are, and that can inform every trait thereafter. In fact, I would ideally port my own snapshot of norms to the users, so that users (most of whom will have a very small database to start) have some point of reference for actual norms rather than the system slowly trying to build norms based off of their own small sample sizes.

But saying "norms" and determining what a permanent norms-constant snapshot looks like are 2 different things. I can see what needs to be done, but the real trick is in deciding what that looks like, and how to make it maximally useful to as many norms-checking algorithms within the app (nearly all the Predictors engines use "norms" as a reference point: Enneagram, Traits, etc. - yes? Which ones don't* use norms and which ones do? Let's look at that and then figure out what we need to save in a permanent norms reference constant.)

So there are a few models I can immediately think of: i) one big norms lookup table, providing a handy report of what the database holds. local traits databases can build their own semipermanent norms-cache off of that only updates to accommodate a newly added trait (adding that trait to the cached norms), or removed (removing that trait from the cached norms), archived (adding the trait to a list of "retired cache" and excluding the "retired" section from norms scans) or un-archived (moving the trait norms from the retired cache and back into the 'include in scans' list). 

ii) separate norms bespoke to each norms-checker, i.e. one just for traits, one for Enneagram, one for Distinguishing Factors, etc. - which may have some overlap but are each self contained, and of which only dynamic caches (of which there is only one: Traits) needs refresh. 

Currently, all norms caches are treated as dynamic, because the database changes/updates/new charts/deleted charts/edited charts are treated as cause for the norms to be recalculated, but ALSO if Traits are added/removed/archived/unarchived/renamed - and that is all wrong, the latter in the short term, the former in the broader scheme of things. My original plan was that caches would only be recalculated if/when the database's astro_data in charts changed more than 10% from the previous cache, but that was clearly very poorly deployed, and any way, I'm seeing it's impractical. I - as the developer, with a huge & diverse database - should just assert that my database is the most normal and provide it as a boilerplate norms constant, not some perpetually recalculating cache! We have the data now, let's assert it & not keep reinventing it! We know what normal is, relatively speaking - let's lock it in and bundle it as a static object, so that recalculation doesn't keep happening. (We can ultimately allow users, at their behest, to resample their own database as a replacement norms constant on demand. But rather than an ongoing recalculation, this will be a one time button-click generation of norms from their database, which generates a new target-constant rather than an ongoing calculation bottleneck like we currently have.)

Then Traits are the only potentially ever-shifting variable. Every other norms-dependent factor is static, baked into the app as a default. Traits is tricky because it provides for user customization. But the way we've been handling that is also stupid. If Traits are added, norms should only be recalculated for EXACTLY JUST the trait that was added. Not all traits norms need to be reassessed against the database! If a trait was deleted, just remove its norms from the Trait norms cache (or stop searching the universal norms cache for that trait's parameters). If a trait is archived/un-archived, I've already addressed that handling above. In short, those are the only changes that should be made to Trait norms - modular, piecemeal, efficient. We should not be rebuilding our entire understanding of how traits relates to the database every time one tiny component of that system changes.



b) As I just alluded: while I like the idea of establishing an Official EphemeralDaddy Norms Constant (or system of constants bespoke to each norm-dependent function within the app's specific demands/queries) to bundling it with the app to circumvent the recurring 'norms calculation' step again and again and again, I *would* like to provide the user (and my future self) with a button in Settings>Developer Tools to "Recalculate DB Norms" manually, which will generate an alternate norms constant to target rather than relying on the boilerplate one that comes bundled in the app. That way a user can compare their own database norms against the developer's (mine) and see how universal they really are. 



3) My future vision for the app is this: I want Traits to be damn near infinitely expandable. I want an individual chart to potentially be scanned for HUNDREDS of traits and find which are the closest matches (well above/below norms), and also be able to near-instantly get a complete ranking of this chart in relation to all traits. I'd like to be able to search quickly by traits & return all charts that are a match in terms of that trait being most highly predicted. This is far better than generic astrological descriptions, because it's based on real data. I'd like to also set up "theoretical" astrological models of traits and compare that to real world observation (defining traits based on people observed to have it and aggregating their charts to create an life-based predictor rather than an astrology-theory-based predictor).

For those goals, it needs to be fast. Traits is intended to eventually be a huge part of the backbone of the app, something that causes it to meaningfully distinguish it from other astro apps. Right now, it's choking. The feature is hard to use, because it's so annoyingly slow. But trust is also important. So it needs to be fast and accurate. I think if we implement these changes I'm explaining, it may take care of both issues significantly. If you see other opportunities for optimization down that pipeline as we've just discussed, let's go ahead and implement them as long as it doesn't override any of these 3 core goals.
